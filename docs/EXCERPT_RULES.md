# 摘录与引用规范（待 review）

适用范围：`site/data/quotes.json` 的摘录增补，以及 `site/data/diary.json` 正文 / summary 里对她说的话的引用。这份文档把历次口头约定集中成一份可逐条核对的标准；与 [WRITING-RULES.md](WRITING-RULES.md) 第 2–5、10、15–17、20 条一致，冲突时以用户当场指定为准。

## 1. 入选门槛

收——满足其一：
- **有哲理**：把一件事讲透，能立住一种看法或人生态度（例：数学是靠习惯而非理解、喜欢的事本身就是心情转换、心大是因为一路都熬过来了）。
- **涨知识 / 讲清楚一件事**：语源、名物、习俗、制度、文字、料理，或把一个提问拆成几层答完。这类比单句俏皮话质量更高。
- **丰富她的人生经历**：她用自己的经历说明一个道理。
- **描述足够精彩**：画面感强、叙述本身出色。

不收：
- **纯玩梗、单句俏皮话**。
- **普普通通的回答**——即使没错，但这类答法之前已经收过太多，再收显得一般。判定标准是"这段话有没有超出日常应答的信息量或哲理"，不是"说得对不对"。
- **每天都说的常规话**：晚安、注意身体、别吵架这类天天重复的收尾叮嘱，单独不收；只有她把一件事讲清楚时才收（如"不希望粉丝吵架，这就是我的想法"作为一段论证的收束）。

主题类需求按用户当场指定放宽，例如"最后那些关于粉丝争吵的，尽可能都摘录"——此时以"主题齐全"优先，不再逐条卡门槛。

## 2. 原文保真（`jp` / `zh`）

**一条摘录 = 讲同一件事的一组逐字稿条目**（2026-11-26 用户定稿）。页面正文直接引用逐字稿，和档案页共用同一份数据：
- 源文件 `jp/zh` 写她讲这件事的那几句，用来给 `gen_data.topic_lines()` 定位主题的首尾；正文由它圈出的 `lines:[{t,jp,zh}]` 提供，**不要在源文件里另写一份和逐字稿不同的正文**。
- 圈段规则：按首句在锚点前 8 行内找起点、末句在后面找终点，把中间所有逐字稿条目整段引用（含口误、插入语）；找不到边界时退回锚点附近。源末句把连续两三句并成一行时整行相似度会被稀释，`topic_lines()` 只在结尾后 15 秒 / 6 行内用末句尾部小句或 `note` 引号里的日语原话补齐——所以 `note` 里要补记原话就用引号写原句，别写概括。
- 页面上的 `jp/zh` 由 `lines` 拼出，源文件与产物里的措辞可能不同——这是设计如此，不是校勘错误。ASR 校勘只改 `tools/asr_fixes.py::FIXES`，重导逐字稿后摘录自动跟着变。
- 单条很长没关系——一个话题整段收、连收多句都可以，长度本身不是问题。
- 她照念 / 复述的观众发言放 `sc`（醒目留言）或 `dm`（弹幕），二选一（见第 4 条），正文不写过程性旁白。

## 3. 校勘口径

- 逐字稿原文以 `translation_history.db` 的 `SourceText` 为准；机器译文翻反、ASR 同音错字时，拿 `sc_message` 观众手写原文 + 她的口播校准后重译。
- 错误归因分三层：**ASR 听错 / 翻译环节错 / 她照念 SC 原文**。翻译环节错不回写数据库；她照念的词即便别扭也照原样写，本意放进上下文讲清楚。
- 判断她某句是不是 ASR 误识，拿实时同传译文交叉验证：本地 ASR 与同传一致 → 原文如此；分歧才考虑听错。
- 人名按 `sc_message.uname` 写真实 ID，不写音译错名；话题按该条 `message` 原文归位，不按机器译文脑补。

## 4. SC / 弹幕承载

- 每条摘录最多带一种引用，二选一：`sc: {name, text}`（付费醒目留言）或 `dm: {name, text}`（普通弹幕 / 评论）。两个字段不要同时写。
- 她用一条弹幕里的提问、梗或建议起头时，用 `dm`；用醒目留言起头时用 `sc`。`name` 按手机库 `uname`，没署名留空；`text` 放观众原文，逐字不改。
- `jp` / `zh` 只放她自己的话——照念 / 复述观众发言的句子直接删，页面上有引用块就够。
- 正文不写过程性旁白，不插"（复述这条 SC）""（她自己的回应）""（照念这条弹幕）"这类括号标注。
- 来源判定：先查 SC 展示窗口（`start_time`–`end_time`，到点消失），念的时候已过期不算 SC；不是 SC 再看同窗口弹幕和实时同传定位真实来源。人名对不上时按内容吻合归位，不硬拼 ID。
- 页面表现：SC 是暖色胶囊，弹幕是冷色胶囊并标「弹幕」；复制文本和图片卡片也会带【弹幕】前缀。

## 5. `note`

只写**校勘依据**：SC 锚点（谁、何时、原文大意）、ASR / 译文错在哪、为什么这样校正、哪些内容没收及原因。不写评价（"很温柔""三观正"），不写编辑过程（"分两段""两段标出"）。

## 6. `tag`

不设白名单：2–4 字、名词性、同一类始终同名。已有标签（`人生` `劝解` `吐槽` `科普` `自嘲` `努力` 等）优先沿用保持连贯，遇到新类别直接新造，别为单条造一次性标签。前端筛选项按条数排序、颜色按标签名 hash 生成，新增标签不用改代码。

## 6b. `title`（标题行概括）

摘录卡标题行 = 圆角 tag + 一句简短概括。源文件可选写 `title`；没写时 `gen_data.quote_title()` 从正文首句自动提炼（跳过「嗯/那个」等填充与感谢 SC 的开头，截到第一个句末标点，最长 30 字）。自动标题只是兜底，觉得不准确就在 `site/data/quotes.json` 的那条里补 `title`，不要改前端或产物。

## 7. 去重与合并

- 已收过的结论不要换个时间戳再收一遍，在 `note` 里带过即可。
- 同一话题被 SC 打断但内容连续的，仍合并成一条，时间戳取最早处，段落之间空行分隔。
- `t` 必须是真实时间戳，`build.py` 靠它把摘录挂到对应场次。

## 8. 引用原话：意译不得冒充原文（日记正文 / summary）

日记正文和 summary 里引用她说过的话，**只有两种合法写法**，任何把概括或意译伪装成她原话的做法都禁止：

1. **原句 + 译文**：写出日语原句，紧跟中文译文，写成「原句」（译文）。原句必须能在逐字稿里逐字找到（ASR 硬错按 `FIXES` 校正后的写法），配的译文也要忠实于原句。
2. **叙述转述**：用自己的话交代她讲了什么，**不加引号、不写成「她说『……』」**。凡是概括、意译、把上下文推出的话，一律走这种。

判定口径：
- **引号内只能是原句**。「彼女は『……』と言った」式写法里，引号内必须是逐字稿里真实存在、且译文忠实的句子。中文概括套进引号（如把「能让心情平静下来」写成「能让她知道就好」）就是冒充。
- **拿不准是不是原话，就当转述**：宁可写成叙述，也不要给概括加引号。分不清某句是她说的还是叙述者的总结时，一律不加引号。
- **指代要跟着原句走**：她原话用「こんなこと」「それ」这类指代时，转述要把指代对象交代清楚（前文说了什么），但不能把交代的内容当成她说的原话塞进引号。例：她说「こんなことされて嫌な気持ちになっちゃった」（因为这种事心里不舒服），「这种事」指前文的私信积压、回复慢——这是**叙述者补的语境**，不是她原话里的「没被回」。
- **翻译环节错不算她的原话**：机器译文断句错、翻反意思（如把「例えば私が犬って言った言葉」直译成「比如说我是狗」），是译文问题，按第 3 条走 `FIXES` 校正；绝不能把错译当成她的原话引用，也不能反过来拿错译去改她的日语。
- **校勘后写进 note**：某句引用做过校正（改译、补字、还原指代），在 `note` 里记依据，正文保持干净。

一句话原则：**引号 = 她的原句 + 忠实译文；其余全是叙述。** 写完后逐条回查引号内容是否在逐字稿里存在、译文是否对得上，答不上来的就去掉引号改成叙述。

## 9. 操作清单

1. 手写逐字稿 → 逐条过，标 ASR 误识、译文翻反、承接哪条 SC / 弹幕。
2. 按第 1 条挑段，按第 2 条照抄原文。
3. 按第 3、4 条校勘、拆 SC / 弹幕，按第 5 条写 `note`，按第 6 条定 `tag`。
4. 跑 `python tools/gen_data.py` → `python tools/build.py`，字幕索引只有时间戳噪声时 `git checkout -- site/data/subs/index.json`。
5. 内容与前端改动分开提交；不 push，除非用户明说。
